零构建静态 PWA + Capacitor Android 原生壳。 没有框架、没有打包器、没有 CSS 预处理器 —— 前端就是浏览器原生 ES Modules 直接跑； 需要系统能力的部分（通知、后台保活、桌面图标、原生定位）用自写 Java 插件补。 整个工程运行时依赖只有 4 个，全部是 Capacitor。

3数据层：多家源，一套接口

中国天气 nmcOpen-Meteowttr.in墨迹天气（逆向）自定义 JSON

  • Provider Registry：每家源声明能力位 byCityName / air / hourly / daily / alert / background 与 nativeOnly。界面按能力位决定「这一栏有没有、这条提示说什么」，而不是给每家源写一个 if。
  • 字段映射 DSL：路径取值 + mul/add 单位换算 + map 码表 + codes:"wmo"|"owm" 补中文描述。只解析 JSON，不执行任何代码。
  • AQI 双标准：中国 HJ 633 与美国 EPA 两套 breakpoint（取自 mee.gov.cn / epa.gov），每枚徽章带可见的出处与标准标注；字色由底色决定（在近黑与白之间取比值更高的那端）。
  • 站点码表：72KB 中国天气站表按需动态 import、刻意不进 SW 清单；坐标做过一轮清洗（重名站会把几百公里外那个省的天气当成用户这里的）。
  • 地名解析：Photon + Open-Meteo 双源合并打分，带类别加权 —— 用户打「X县」时不许被别省同名的更高级别点顶掉。
  • 数据诚信约束：宁缺勿错 —— 缺测不许退成 0，别城的报文不许画在本城卡上，拿不到就明说。判「取到了」的最后一道闸是结构（这一页里到底有没有天气），不是状态码。

6值得单独讲的五条

  1. 无构建链是主动选择，不是偷懒。源码即产物，「构建后行为不一致」这类问题不存在；代价是要自己管缓存版本（SW 的 CACHE 号）和请求数（63 个模块里入口那张静态图占 62 发请求（第 63 个是动态 import 的站点码表），靠壳里的本地文件消化掉）。按归属分片那一轮把这笔账量了：入口静态图 38 → 62，DCL +15ms、首屏「温度到位」+5ms，而 FCP 48ms 没动 —— 换来的是「每条新功能都得改同一个文件」那个冲突现场没了。
  2. 测量通道本身会坏。这个项目里最贵的几次 bug 都不是代码坏了，而是「看起来在测、其实什么都没测」：锁屏下 getComputedStyle 给半新半旧的读数、后台标签被节流到每分钟一个宏任务、假响应表照着实现写（实现错了它照样「成功」回答）。所以每条断言都要被改坏实现逼红一次才算数。
  3. 可访问性是量的，不是看的。2 套主题 × 各自六条渐变 × 四个色标（主文字 / 次要文字 / --pop / --accent）逐元素往上合成真实底色，渐变按每个色标各算一次取最坏（WCAG F83）；达标线是 AA(4.5) 再加 0.5 余量。本轮实测最低：薄荷蓝 5.01、夜航 5.33。
  4. 逆向数据源要连失败路径一起断言。同一家常见三种「200 但正文不是数据」的形态（限流文案、404 模板、改版空壳），只看状态码一律算取到，界面就成了一张全 -- 的空屏 —— 空屏比报错更坏，因为它会被读成「今天没数据」。
  5. 原生能力的边界要在界面上说实话。桌面图标只能在那 4 套预设里换（图标是编译期资源），所以那一栏压根没有「从相册选图」按钮，而不是放个灰按钮让人以为坏了。
